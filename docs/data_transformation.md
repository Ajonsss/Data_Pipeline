# Data Transformation Documentation

## 1. Transformation Input and Processing Specification

### 1.1 Input Source

The Transformation Input and Processing Stage is designed to receive the academic data extracted by Stage 1 of the EduLite Assessment Analytics ETL Pipeline. It will use the output files and extraction logs generated by `extraction.py` as its input. This stage will process the extracted data without connecting to or re-extracting data from the source database.

- **Input Source:** Output files generated by the Extraction Stage.
- **Format:** JSON files.
- **Input Location:** `data/raw/`
- **Extraction Metadata:** `data/logs/extraction_logs.jsonl`
- **Extraction Run ID:** Retrieved from the `pipeline_run_id` field in the extraction log. The current format is `EXT_YYYYMMDD_HHMM`, for example, `EXT_20261022_0915`.
- **Batch Window:** `FULL`, meaning all records included in the selected successful full extraction will be processed.

The input consists of the following files:

| Input File | Description |
|---|---|
| `students.json` | Student records, including names, grade levels, and section references. |
| `sections.json` | Section records used to identify students' class sections. |
| `subjects.json` | Subject records used to identify academic subjects. |
| `assessments.json` | Assessment records, including subject references and total items. |
| `assessmentScores.json` | Student assessment scores linked to students and assessments. |

Before processing, the stage is expected to verify that the required output files are available and that their record counts match the corresponding extraction logs. It will also identify the successful extraction run to be processed.

### 1.2 Batch Processing Method

The proposed processing method uses Python scripts to prepare, validate, and clean the extracted JSON files.

- **Processing Technology:** Python, JSON processing, and `bson.json_util` for MongoDB-compatible data where needed.
- **Processing Script:** `transformation_input.py` will prepare and validate the extracted input before subsequent processing stages.
- **Batch Frequency:** Daily at 12:00 AM, as the intended schedule, with manual execution when needed. Automatic execution requires a configured scheduler or Prefect deployment. Automatic execution will require a configured Prefect deployment or another scheduler.
- **Batch Size:** Full-batch processing. All records from the selected successful extraction will be processed, without a fixed record limit or incremental time window.
- **Failure Handling:** If required files are missing, invalid, or inconsistent with the extraction logs, processing should stop and record or report the error. After the problem is corrected, the same extracted input can be processed again without re-extracting it from the source database.
- **Rerun and Idempotency:** The stage is intended to support rerunning the same extracted batch. To ensure idempotency, repeated processing must produce consistent results without creating duplicate output records or unintended changes. This behavior must be verified through implementation and testing.

The planned processing sequence is:

1. **Stage 1 – Extraction:** `extraction.py` extracts the academic data and generates JSON files in `data/raw/`, together with extraction logs.
2. **Transformation Input:** `transformation_input.py` identifies the extraction batch and checks the availability and consistency of its input files.
3. **Data Profiling:** A subsequent processing stage will examine data quality and generate a report at `data/profiling/data_quality_issues.csv`.
4. **Data Cleaning:** A subsequent processing stage will apply the defined cleaning rules and save accepted records in `data/cleaned/`.

Only Stage 1 is currently implemented. The remaining steps describe the planned processing workflow and should not be considered automatically scheduled or completed.

### 1.3 Transformation Scope

The planned input-processing workflow covers the five JSON files produced by Stage 1: students, sections, subjects, assessments, and assessment scores.

The intended scope includes:

- **Input validation:** Verify the expected files, required fields, and record counts against the extraction handover.
- **Data profiling:** Identify missing required values, duplicate identifiers, invalid data types or values, assessment scores exceeding the assessment's total items, broken references, and unnecessary whitespace.
- **Data cleaning:** Standardize text by trimming leading and trailing whitespace, validate required fields and numeric values, identify duplicate records, and flag or reject records with invalid values or broken references according to the defined cleaning rules.
- **Output preparation:** Prepare the extracted data for later profiling and cleaning. The planned downstream stages will generate quality reports, cleaned JSON files, rejection logs, and processing summaries.

Calculating final grades, averages, or aggregated student performance measures is outside the current Stage 1 extraction scope. These calculations can be implemented in a later transformation stage.

### 1.4 Dependencies and Assumptions

The planned processing stage depends on the successful completion of Stage 1 and the availability of its JSON output files and extraction logs.

The expected processing order follows the relationships between the records:

1. **Sections and Subjects:** Provide reference identifiers for validating student and assessment records.
2. **Students:** Reference their corresponding sections.
3. **Assessments:** Reference their corresponding subjects.
4. **Assessment Scores:** Reference their corresponding students and assessments.

The workflow assumes that the extracted files follow the expected JSON structure, contain the identifiers needed to validate record relationships, and are accurately represented in the extraction logs.

The current extraction design uses full-batch processing, and files in `data/raw/` may be overwritten by a later extraction. Therefore, reliable reprocessing of a historical batch requires preserving a versioned copy of its input files. Matching record counts alone does not prove that the current files belong to a particular historical extraction run.

If a required reference record is missing, the affected record will be flagged or rejected according to the applicable cleaning rule in the planned downstream stage. The transformation stage is not expected to re-extract missing information from the source database.

## 2. Data Profiling and Issue Identification

### 2.1 Purpose

Data profiling is performed to examine the extracted academic data and identify data quality issues before applying the cleaning rules. The profiling stage uses the JSON files generated by Stage 1 of the EduLite Assessment Analytics ETL Pipeline. It does not extract data again from the source database or modify the original raw files.

The profiling process examines five files: `students.json`, `sections.json`, `subjects.json`, `assessments.json`, and `assessmentScores.json`. It checks for missing required values, duplicate identifiers, invalid data types or values, broken references, assessment scores exceeding the total assessment items, and unnecessary whitespace.

### 2.2 Data Quality Issues and Planned Treatment

The following table lists the data quality issues checked by the profiling process. The examples are illustrative; actual examples and affected-record counts must be obtained from the profiling results.

| Table or File | Column | Issue Type | Example | Affected Records | Planned Treatment |
|---|---|---|---|---|---|
| `students.json` | `name` | Missing value | `null` or missing field | To be determined by profiling | Flag or reject records with missing required fields (Rule C-01) |
| `students.json` | `_id` | Duplicate identifier | Same identifier appearing more than once | To be determined by profiling | Keep the first occurrence and reject subsequent duplicates (Rule C-02) |
| `students.json` | `name` | Unnecessary whitespace | `"  Juan Dela Cruz  "` | To be determined by profiling | Remove leading and trailing whitespace (Rule S-01) |
| `students.json` | `grade` | Invalid data type or value | `"Grade 5"` or `0` | To be determined by profiling | Validate the numeric type and acceptable value (Rules C-03 and C-04) |
| `sections.json` | `_id` | Duplicate identifier | Same section identifier appearing more than once | To be determined by profiling | Keep the first occurrence and reject subsequent duplicates (Rule C-02) |
| `subjects.json` | `name` | Missing value or unnecessary whitespace | `null` or `" Mathematics "` | To be determined by profiling | Flag missing required fields (Rule C-01) and trim whitespace (Rule S-01) |
| `assessments.json` | `totalItems` | Invalid data type or value | `"20"` or `0` | To be determined by profiling | Validate the numeric type and require a positive value (Rules C-03 and C-04) |
| `assessments.json` | `subjectId` | Broken reference | Identifier does not exist in `subjects.json` | To be determined by profiling | Reject or flag records with missing references (Rule C-05) |
| `assessmentScores.json` | `score` | Invalid data type or value | `"15"` or `-2` | To be determined by profiling | Validate the numeric type and acceptable range (Rules C-03 and C-04) |
| `assessmentScores.json` | `score` | Score exceeds assessment total | Score of `25` when `totalItems` is `20` | To be determined by profiling | Reject or flag scores exceeding the assessment total (Rule C-04) |
| `assessmentScores.json` | `studentId` | Broken reference | Student identifier does not exist in `students.json` | To be determined by profiling | Reject or flag records with missing references (Rule C-05) |
| `assessmentScores.json` | `assessmentId` | Broken reference | Assessment identifier does not exist in `assessments.json` | To be determined by profiling | Reject or flag records with missing references (Rule C-05) |

**Note:** The table describes the issues being checked, not confirmed findings. Rows should be retained as actual findings only when profiling detects those issues. If no issues are found for a particular check, report zero affected records or omit the issue from the findings table, depending on your required reporting format.

### 2.3 Profiling Method

The profiling script, `data_profiling.py`, reads the extracted JSON files from `data/raw/` and checks the records against the required fields, expected data types, acceptable values, and relationships between collections.

The profiling process follows these steps:

1. Read the extraction logs and identify the latest successful extraction run.
2. Load the corresponding raw JSON files and verify their record counts against the extraction logs.
3. Check for missing required fields, duplicate identifiers, invalid types or values, unnecessary whitespace, and broken references.
4. Compare assessment scores with the total items of their corresponding assessments.
5. Record detected issues, sample values, affected-record counts, and planned treatments.
6. Generate the data quality report in `data/profiling/data_quality_issues.csv`.

### 2.4 Profiling Output

The profiling report is saved as:

`data/profiling/data_quality_issues.csv`

The report contains the following columns:

- **Table:** The source JSON file or collection containing the issue.
- **Column:** The field where the issue was identified.
- **Issue Type:** The category of the data quality issue.
- **Example:** A sample value illustrating the issue.
- **Affected Records:** The number or percentage of records affected, based on the profiling results.
- **Planned Treatment:** The cleaning action and corresponding rule reference.

The profiling report provides the information needed to determine which cleaning rules should be applied during the subsequent Data Cleaning Stage. The original extracted JSON files remain unchanged during profiling.

## 3. Data Cleaning Rules

The data cleaning stage corrects formatting issues and rejects records that fail the defined data-quality checks. The pipeline processes the extracted EduLite JSON files and saves the cleaned records separately in `data/cleaned/`. The original raw files are preserved.

Each rejected record is counted and recorded in `data/logs/rejected_records.jsonl`. A summary of input, cleaned, and rejected records is saved in `data/logs/cleaning_logs.jsonl`.

### 3.1 Cleaning Rules

| Rule ID | Target | Condition | Action | Justification |
|---|---|---|---|---|
| C-01 | Required fields in all five files | Required field is missing, null, or blank | Reject and log the record | Prevents incomplete records from entering later processing. |
| C-02 | All files: `_id` | Duplicate identifier is detected | Keep the first occurrence and reject and log subsequent occurrences | Prevents duplicate identifiers from being included in the cleaned output. |
| C-03 | `students.grade`, `assessments.totalItems`, `assessmentScores.score` | Value is not an integer | Reject and log the record | Ensures numeric fields use the expected data type. |
| C-04 | `students.grade` | Grade is zero or negative | Reject and log the record | Prevents invalid grade-level values. |
| C-04 | `assessments.totalItems` | Total items is zero or negative | Reject and log the record | Ensures assessments have a valid positive number of items. |
| C-04 | `assessmentScores.score` | Score is negative or exceeds the assessment's total items | Reject and log the record | Prevents scores outside the defined assessment range. |
| C-05 | `students.sectionId` | Referenced section does not exist in the cleaned sections data | Reject and log the record | Prevents student records from referencing nonexistent sections. |
| C-05 | `assessments.subjectId` | Referenced subject does not exist in the cleaned subjects data | Reject and log the record | Ensures assessments are associated with existing subjects. |
| C-05 | `assessmentScores.studentId`, `assessmentScores.assessmentId` | Referenced student or assessment does not exist in the cleaned data | Reject and log the record | Prevents assessment scores from becoming orphan records. |
| S-01 | `name` fields in all five files where present | Name contains leading or trailing whitespace | Trim the whitespace | Improves consistency when comparing or matching names. |

### 3.2 Duplicate Handling

When duplicate `_id` values are found in the same file, the pipeline retains the first occurrence and rejects subsequent occurrences. Every rejected duplicate is logged. The pipeline does not assume that a record is more accurate simply because it appears later in the file.

### 3.3 Missing and Invalid Values

Records with missing required fields are rejected rather than silently filled with default values. Invalid numeric types and values are also rejected and logged. The pipeline does not invent missing student, subject, section, assessment, or score information.

### 3.4 Orphan Records

The pipeline checks the relationships between students and sections, assessments and subjects, and assessment scores and their related students and assessments. Records with unresolved references are rejected and logged so they can be reviewed against the source data.

### 3.5 Logging and Output

The cleaned files are written to `data/cleaned/`, while rejected-record details are written to `data/logs/rejected_records.jsonl`. The cleaning summary records the number of input records, cleaned records, and rejected records for each file.

This process ensures that rejected records are not silently dropped and that the raw extracted data remains available for investigation or reprocessing.

## 4. Standardization and Data Type Rules

### 4.1 Purpose

Standardization and data type rules ensure that extracted EduLite academic data follows consistent formats and valid data types before being used in further transformation and analysis. The cleaning process applies these rules to five collections: sections, subjects, students, assessments, and assessment scores.

The rules help identify missing values, duplicate identifiers, invalid numeric values, and references to records that do not exist. Records that fail validation are excluded from the cleaned output and recorded in the rejection log.

### 4.2 Data Types

The following table defines the expected data types and validation rules for the important fields in the EduLite ETL pipeline.

| Column | Collection | Expected Data Type | Validation Rule |
|---|---|---|---|
| `_id` | All collections | MongoDB identifier | Must be present and non-missing. Duplicate IDs are rejected, and the first occurrence is retained. |
| `name` | Sections, Subjects, Students, Assessments | String | Leading and trailing whitespace is removed. The value must not be missing or empty after trimming. |
| `grade` | Students | Integer | Must be an integer greater than zero. |
| `sectionId` | Students | MongoDB identifier | Must reference an existing section in the cleaned data. |
| `subjectId` | Assessments | MongoDB identifier | Must reference an existing subject in the cleaned data. |
| `totalItems` | Assessments | Integer | Must be an integer greater than zero. |
| `studentId` | Assessment Scores | MongoDB identifier | Must reference an existing student in the cleaned data. |
| `assessmentId` | Assessment Scores | MongoDB identifier | Must reference an existing assessment in the cleaned data. |
| `score` | Assessment Scores | Integer | Must be an integer greater than or equal to zero and must not exceed the assessment's `totalItems`. |

The cleaning script validates numeric fields but does not automatically convert numeric strings or decimal values into integers. A value must already be a valid integer to pass the implemented numeric validation.

### 4.3 Standard Formats

#### Text Standardization

The cleaning process applies Rule S-01 to the `name` field in all four applicable collections. It removes unnecessary whitespace from the beginning and end of a name while preserving its original capitalization and spelling.

For example, `"  Mathematics  "` becomes `"Mathematics"`. The script does not convert names to uppercase or title case.

#### Numeric Standardization

The `grade`, `totalItems`, and `score` fields are checked to ensure that they contain valid integer values.

- `grade` must be greater than zero.
- `totalItems` must be greater than zero.
- `score` must not be negative.
- `score` must not exceed the corresponding assessment's `totalItems`.

The pipeline does not apply rounding because these fields are validated as integers. If decimal scores or calculated averages are introduced later, their precision and rounding rules should be documented separately.

#### Identifier Standardization

MongoDB identifiers and their related reference fields are preserved using MongoDB-compatible JSON serialization. The cleaning process compares their string representations to determine whether related records exist.

The identifiers are not converted to UUIDs or another identifier format by the current cleaning script.

### 4.4 Reference Values and Codes

The current pipeline does not contain currency, measurement units, country codes, or gender fields. Therefore, standardization mappings for these values are not applicable to the current extraction scope.

Instead, the cleaning process validates relationships between collections using Rule C-05.

| Collection | Reference Field | Referenced Collection | Validation |
|---|---|---|---|
| Students | `sectionId` | Sections | The referenced section must exist in the cleaned sections data. |
| Assessments | `subjectId` | Subjects | The referenced subject must exist in the cleaned subjects data. |
| Assessment Scores | `studentId` | Students | The referenced student must exist in the cleaned students data. |
| Assessment Scores | `assessmentId` | Assessments | The referenced assessment must exist in the cleaned assessments data. |

Records with missing or unmatched references are rejected from the cleaned output and recorded in `data/logs/rejected_records.jsonl`.

### 4.5 Handling Conversion and Validation Failures

The cleaning process uses validation rather than automatic data type conversion. If a value does not satisfy the required format or validation rule, the affected record is excluded from the cleaned output.

The following rules are applied:

| Rule ID | Validation Rule | Action |
|---|---|---|
| C-01 | Required values are missing or empty. | Reject the record and log the reason. |
| C-02 | A duplicate `_id` is found. | Reject the duplicate record while retaining the first occurrence. |
| C-03 | A numeric field does not contain a valid integer. | Reject the record and log the invalid field. |
| C-04 | A numeric value violates its permitted range. | Reject the record and log the reason. |
| C-05 | A reference does not match an existing parent record. | Reject the record and log the unmatched reference. |
| S-01 | A name contains leading or trailing whitespace. | Trim the whitespace before validating and saving the record. |

Rejected records are recorded in `data/logs/rejected_records.jsonl`. The log includes the collection name, record index, record identifier, rejection reasons, timestamp, and rejection action. The cleaning process saves accepted records as separate JSON files in `data/cleaned/`, leaving the raw extraction files separate.

### 4.6 Output and Logging

After cleaning and validation, the pipeline generates cleaned JSON files for the five collections in the `data/cleaned/` directory. It also records the cleaning run ID, start and end timestamps, execution status, input counts, cleaned counts, and rejected counts in `data/logs/cleaning_logs.jsonl`.

These outputs provide a record of the cleaning process and help identify how many records were retained or rejected during each run.


## 5. Business Transformation Rules

The Business Transformation Rules define how cleaned student, subject, assessment, and assessment-score data are converted into business-ready student performance records. These rules include joining related records, grouping assessments by category, calculating percentages and weighted scores, and checking assessment completeness based on the EduLITE grading rules.

### 5.1 Business Transformation Rules

| Rule ID | Input Columns | Logic / Formula | Output Column | Business Reason |
|---|---|---|---|---|
| B-01 | `students._id`, `students.sectionId`, `students.grade`, `sections._id` | Match each student's `sectionId` with the corresponding section record. | Student-section relationship | Identifies the section and grade level associated with each student. |
| B-02 | `students._id`, `subjects._id`, `assessments.subjectId` | Match assessments to their corresponding subjects and organize results by student and subject. | Student-subject assessment records | Ensures assessment results are associated with the correct student and subject. |
| B-03 | `assessments.classSections`, `students.grade`, `students.sectionId` | If `classSections` is empty or null, treat the assessment as subject-wide. Otherwise, include it only when the student's grade and section match an assigned class section. | Applicable assessments | Ensures students are evaluated only using assessments intended for their class or section. |
| B-04 | `assessmentScores.studentId`, `assessmentScores.assessmentId`, `assessmentScores.score` | Match scores using the combination of `studentId` and `assessmentId`. A missing score record is currently treated as zero. | Student assessment score lookup | Connects each student's score to the correct assessment. |
| B-05 | `assessments.category`, `assessmentScores.score`, `assessments.totalItems` | Group all applicable assessments with the category `written_work`. Add their scores and HPS, then calculate `(Total WW Score / Total WW HPS) * 100`. | Written Work Percentage | Calculates the student's overall Written Work performance, supporting multiple assessments. |
| B-06 | `assessments.category`, `assessmentScores.score`, `assessments.totalItems` | Group all applicable assessments with the category `performance_task`. Add their scores and HPS, then calculate `(Total PT Score / Total PT HPS) * 100`. | Performance Task Percentage | Calculates the student's overall Performance Task performance, supporting multiple assessments. |
| B-07 | `assessments.category`, `assessments.sequence`, `assessmentScores.score`, `assessments.totalItems` | Identify the Summative Test assessments using sequence numbers 1 and 2. Calculate each percentage separately: `(Assessment Score / HPS) * 100`. | ST1 Percentage, ST2 Percentage | Calculates the two Summative Test results separately according to their sequence numbers. |
| B-08 | `assessments.category`, `assessments.sequence`, `assessmentScores.score`, `assessments.totalItems` | Identify the Term Examination using sequence number 1. Calculate `(Term Exam Score / HPS) * 100`. | Term Examination Percentage | Calculates the student's Term Examination performance. |
| B-09 | Written Work Percentage, Performance Task Percentage, ST1 Percentage, ST2 Percentage, Term Examination Percentage | Multiply Written Work by 20%, Performance Task by 50%, and the Summative component by 30%. The Summative component is calculated as `(ST1 * 0.30) + (ST2 * 0.30) + (Term Exam * 0.40)`. | Weighted Assessment Scores | Applies the prescribed EduLITE grading weights to each assessment category. |
| B-10 | Weighted Written Work, Weighted Performance Task, Weighted Summative Component | Add the three weighted scores: `WW Weighted + PT Weighted + Summative Weighted`. | Initial Grade | Produces the student's initial grade for a specific subject and academic term. |
| B-11 | `assessments.term`, `assessments.subjectId`, `students._id` | Organize the assessment results by student, subject, and academic term (1, 2, and 3). | Student-Subject-Term Records | Keeps student performance results organized according to the academic grading period. |
| B-12 | Required assessment records and calculated components | Check whether the required assessment components are available. The code expects one ST1, one ST2, and one Term Examination. It marks results incomplete when required components are missing or when multiple assessments match a required sequence. | Term Grade Status | Identifies results that are not yet ready for complete grade computation. |

### 5.2 Filtering and Conditional Logic

The transformation process also applies conditions to determine which records are included in the computation.

| Rule ID | Input Columns | Logic | Output | Business Reason |
|---|---|---|---|---|
| B-13 | `assessments.term` | Process assessment records according to their academic term. | Term-specific results | Prevents assessments from different terms from being combined. |
| B-14 | `assessments.category` | Use the `category` field to identify Written Work, Performance Task, Summative Test, and Term Examination. The legacy `type` field is not used for category identification. | Categorized assessment records | Ensures assessments follow the current EduLITE assessment classification. |
| B-15 | `assessments.sequence` | For Summative Tests, identify sequence 1 as ST1 and sequence 2 as ST2. For Term Examination, identify sequence 1. | Sequence-specific assessment records | Ensures the correct assessment is used in each grading component. |

### 5.3 Output of Business Transformation

The Transformation Stage generates the following files:

| Output File | Description |
|---|---|
| `student_subject_results.json` | Contains student performance results organized by subject, including assessment percentages and weighted scores. |
| `term_grade_results.json` | Contains the student's term-level results, including the Initial Grade and computation status. |
| `excluded_records.json` | Contains records identified as excluded or not fully processable during transformation. |

The generated files are saved in the `data/transformed/` directory.

### 5.4 Dimensional Modeling

Dimensional modeling is not currently implemented in this stage. The transformation process does not create separate fact or dimension tables, generate surrogate keys, or apply Slowly Changing Dimension techniques. Instead, it organizes the transformed academic data into JSON files for the subsequent loading stage.

### 5.5 Implementation Notes

The following implementation details should be considered when finalizing the transformation code:

1. **Missing Written Work or Performance Task assessments:** The grading manual states that a category with no created assessments should be excluded from the computation. However, the current code marks the result incomplete when either category has no assessments. The code should be updated to follow the grading rule.
2. **Transmutation:** The current code calculates the Initial Grade but does not yet apply the transmutation table to produce the Term Grade.
3. **Final Grade:** The Final Grade cannot yet be calculated because the transmuted Term Grades are not available.
4. **Business exclusions:** The current code applies assessment applicability rules, but it does not implement a separate business-status exclusion rule, such as excluding cancelled assessments. Such a rule should only be documented if it is implemented.





## 6. Transformed Data Contract and Naming Convention

The Transformed Data Contract defines the expected structure, data types, and naming conventions of the data generated by the Transformation Stage. It ensures that the transformed student performance records are consistently organized and ready to be received by the Load Stage for storage in the separate Supabase PostgreSQL database.

### 6.1 Required Output Schema

The Transformation Stage generates three JSON output files. Each file serves a specific purpose in organizing student performance results and identifying records that require attention.

#### 6.1.1 Student Subject Results

**Output File:** `student_subject_results.json`

**Description:** Contains the transformed assessment results of each student, organized by subject. It includes calculated assessment percentages and weighted scores for Written Work, Performance Task, Summative Tests, and Term Examination.

| Column Name | Data Type | Nullability | Description |
|---|---|---|---|
| `student_id` | String | Required | Unique identifier of the student. |
| `subject_id` | String | Required | Unique identifier of the subject. |
| `term` | Integer | Required | Academic term, with values 1, 2, or 3. |
| `written_work_percentage` | Number | Nullable | Calculated Written Work percentage. |
| `performance_task_percentage` | Number | Nullable | Calculated Performance Task percentage. |
| `st1_percentage` | Number | Nullable | Calculated percentage for Summative Test 1. |
| `st2_percentage` | Number | Nullable | Calculated percentage for Summative Test 2. |
| `term_exam_percentage` | Number | Nullable | Calculated Term Examination percentage. |
| `written_work_weighted` | Number | Nullable | Written Work percentage multiplied by 20%. |
| `performance_task_weighted` | Number | Nullable | Performance Task percentage multiplied by 50%. |
| `summative_weighted` | Number | Nullable | Summative component percentage multiplied by 30%. |
| `initial_grade` | Number | Nullable | Sum of the three weighted assessment components. |

#### 6.1.2 Term Grade Results

**Output File:** `term_grade_results.json`

**Description:** Contains the organized term-level performance results of each student for every subject. It includes the Initial Grade and the computation status of the term grade.

| Column Name | Data Type | Nullability | Description |
|---|---|---|---|
| `student_id` | String | Required | Unique identifier of the student. |
| `subject_id` | String | Required | Unique identifier of the subject. |
| `term` | Integer | Required | Academic term, with values 1, 2, or 3. |
| `initial_grade` | Number | Nullable | Calculated initial grade before transmutation. |
| `term_grade` | Number | Nullable | Transmuted term grade. Currently null until the transmutation process is implemented. |
| `term_grade_status` | String | Required | Indicates whether the term grade computation is complete or awaiting transmutation. |
| `final_grade` | Number | Nullable | Final grade calculated from the three transmuted term grades. Currently unavailable until term grade computation is implemented. |

#### 6.1.3 Excluded Records

**Output File:** `excluded_records.json`

**Description:** Contains records identified during transformation that cannot be fully processed or included in the expected calculations.

| Column Name | Data Type | Nullability | Description |
|---|---|---|---|
| `student_id` | String | Nullable | Identifier of the affected student, when available. |
| `subject_id` | String | Nullable | Identifier of the affected subject, when available. |
| `term` | Integer | Nullable | Academic term associated with the record, when available. |
| `reason` | String | Required | Explanation of why the record was excluded or could not be fully processed. |

**Note:** The fields listed above describe the intended logical output structure. Exact field names and nullability must be checked against the actual JSON generated by `transformation.py` before finalizing the contract.

### 6.2 Naming Convention

The Transformation Stage follows consistent naming conventions to make the generated data easier to understand, maintain, and load into the destination database.

| Naming Element | Convention | Example |
|---|---|---|
| Output files | Lowercase snake_case | `student_subject_results.json` |
| Column names | Lowercase snake_case | `student_id`, `subject_id` |
| Identifier columns | Use the `_id` suffix | `student_id`, `subject_id` |
| Percentage columns | Use the `_percentage` suffix | `written_work_percentage` |
| Weighted score columns | Use the `_weighted` suffix | `written_work_weighted` |
| Grade columns | Use the `_grade` suffix | `initial_grade`, `term_grade` |
| Academic term | Use `term` | `term` |

The current transformation process generates JSON files rather than separate dimensional tables. Therefore, prefixes such as `dim_` and `fact_` are not currently used. These prefixes may be introduced later if dimensional modeling is implemented in the destination database.

## 6.3 Source-to-Target Mapping

The following table describes how the original cleaned data is used to produce the transformed output fields.

| Source Column | Target Column | Source Type | Target Type | Transformation Applied |
|---|---|---|---|---|
| `students._id` | `student_id` | ObjectId | String | Convert MongoDB ObjectId to string. |
| `subjects._id` | `subject_id` | ObjectId | String | Convert MongoDB ObjectId to string. |
| `assessments.term` | `term` | Number | Integer | Preserve the academic term when organizing results. |
| `assessments.category` | Assessment category | String | String | Group assessments according to their category. |
| `assessments.sequence` | Assessment sequence | Number | Integer | Identify ST1, ST2, and Term Examination using their sequence numbers. |
| `assessmentScores.studentId` | Student assessment relationship | ObjectId | String | Match the assessment score to the corresponding student. |
| `assessmentScores.assessmentId` | Assessment relationship | ObjectId | String | Match the score to the corresponding assessment. |
| `assessmentScores.score` | Assessment score | Number | Number | Use the matched student score in the category calculations. |
| `assessments.totalItems` | HPS | Number | Number | Use the assessment's highest possible score as the calculation denominator. |
| Assessment scores and HPS | `written_work_percentage` | Number | Number | Aggregate all applicable Written Work scores and HPS, then calculate the percentage. |
| Assessment scores and HPS | `performance_task_percentage` | Number | Number | Aggregate all applicable Performance Task scores and HPS, then calculate the percentage. |
| Assessment score and HPS for ST1 | `st1_percentage` | Number | Number | Calculate the ST1 percentage separately. |
| Assessment score and HPS for ST2 | `st2_percentage` | Number | Number | Calculate the ST2 percentage separately. |
| Assessment score and HPS for Term Examination | `term_exam_percentage` | Number | Number | Calculate the Term Examination percentage separately. |
| Assessment percentages | Weighted score columns | Number | Number | Apply the prescribed grading weights of 20%, 50%, and 30%. |
| Weighted score columns | `initial_grade` | Number | Number | Add the three weighted assessment components. |

### 6.4 Schema Consistency

The Transformation Stage relies on the cleaned data generated by the Cleaning Stage. It expects the required student, subject, assessment, and assessment-score fields to retain their expected names and data structures.

The following rules are established to maintain schema consistency:

1. **Required Fields:** Required fields used in calculations and record matching must be available. Missing or invalid data should be handled by the Cleaning Stage or identified during transformation.
2. **Data Types:** Identifiers must be converted into strings for consistent representation in the JSON output. Academic terms and sequence numbers must retain their expected numeric values.
3. **Assessment Categories:** The transformation process uses the `category` field to identify Written Work, Performance Task, Summative Test, and Term Examination. The legacy `type` field is not used for category identification.
4. **Unexpected Fields:** Additional fields that are not required by the transformation process are not used in the calculations.
5. **Missing or Changed Fields:** If an expected field is renamed, removed, or changes its data type, the transformation process may fail or produce incomplete results. Such changes must be reviewed and the transformation code updated when necessary.

### 6.5 Keys and Relationships

The transformed records retain student and subject identifiers to preserve traceability to the original EduLITE data.

| Key | Description |
|---|---|
| `student_id` | Identifies the student associated with the performance result. |
| `subject_id` | Identifies the subject associated with the performance result. |
| `term` | Identifies the academic term associated with the result. |

A logical composite key consisting of `student_id`, `subject_id`, and `term` can identify a student's result for a particular subject and academic term.

The current transformation process does not generate surrogate keys or implement separate primary key and foreign key constraints because its outputs are JSON files. These constraints can be defined when the transformed data is loaded into Supabase PostgreSQL.

### 6.6 Data Contract for the Load Stage

The Load Stage is expected to receive the three generated JSON files containing the transformed student performance results, term-level grade information, and excluded records.

The transformed data must retain consistent identifiers, data types, and field names so that it can be stored and queried reliably in the separate ETL database.

The current output is designed for student performance analytics and reporting. It does not yet implement dimensional tables, surrogate keys, or database constraints. These may be introduced during the database loading and modeling process.

## 7. Transformation Validation and Data Quality Checks

The Transformation Validation Stage verifies that the transformed EduLITE Assessment Analytics data is accurate, complete, consistent, and suitable for loading into the separate Supabase PostgreSQL database.

This stage checks the generated student-subject results, term grade records, and excluded records to identify missing values, duplicate results, invalid references, incorrect calculations, and violations of the grading rules.

The validation process also verifies that the computed assessment percentages, weighted scores, Initial Grades, available transmuted Term Grades, and Final Grades follow the prescribed grading computation rules.

Validation results are classified as critical errors or non-critical warnings. Critical failures prevent the validation process from completing successfully, while non-critical warnings are recorded for review without automatically stopping the pipeline.

### 7.1 Validation Checks

The Transformation Validation Stage performs the following checks to ensure the accuracy and consistency of transformed data.

| Check Name | Target | Purpose | Validation Criteria | Severity |
|---|---|---|---|---|
| Output File Check | `student_subject_results.json`, `term_grade_results.json`, `excluded_records.json` | Ensure the required transformation outputs are available. | All three files must exist, be readable, and contain valid JSON arrays. | Critical |
| Required Field Check | `term_grade_results.json` | Ensure essential identifiers and academic term information are available. | `student_id`, `subject_id`, and `term` must not be null or empty. | Critical |
| Key Uniqueness Check | `term_grade_results.json` | Prevent duplicate student-subject-term results. | Each combination of `student_id`, `subject_id`, and `term` must be unique. | Critical |
| Student Referential Integrity | Student identifiers in transformed outputs | Ensure transformed results reference existing students. | Student IDs must match records in cleaned `students.json`. | Critical |
| Subject Referential Integrity | Subject identifiers in transformed outputs | Ensure transformed results reference existing subjects. | Subject IDs must match records in cleaned `subjects.json`. | Critical |
| Term Validity Check | `term_grade_results.json` | Ensure valid academic terms are used. | Term values must be integers from 1 to 3. | Critical |
| Data Type Check | Identifiers, terms, and grade values | Ensure transformed data follows expected data types. | Identifiers must be strings, term values must be integers, and grade values must be numeric or null when incomplete. | Critical |
| Percentage Range Check | Assessment percentage fields | Prevent invalid percentage values. | Calculated percentages must be between 0 and 100. | Critical |
| Initial Grade Check | `term_grade_results.json` | Verify the fixed grading weights and Initial Grade calculations. | Weighted component scores must follow the 20% Written Work, 50% Performance Task, and 30% Summative rules. | Assessment Calculation Check | Nested assessment components | Verify assessment percentages and Summative component calculations. | Written Work and Performance Task percentages must be calculated using total earned scores divided by total HPS. | Term Grade Transmutation Check | `term_grade_results.json.term_grade` | Verify official Term Grade conversion. | Available Term Grades must match the configured transmutation table. | Critical |

The validation process checks the structure and mathematical consistency of the generated outputs.

Assessment matching and sequence handling are primarily performed during the Transformation Stage. This includes selecting applicable assessments by subject and term, checking student and assessment ownership, identifying duplicate assessment sequences, and determining whether the required ST1, ST2, and Term Examination assessments are available.

The Transformation Validation Stage then checks the resulting assessment calculations and grading outputs.

#### Grading Computation Rules

The following grading rules are used during transformation and checked against the generated results.

**Written Works — 20%**

Written Work Percentage = (Total Written Work Scores / Total Written Work HPS) × 100

Written Work Weighted Score = Written Work Percentage × 0.20

Only assessments that were actually created and are applicable to the learner are included.

**Performance Tasks — 50%**

Performance Task Percentage = (Total Performance Task Scores / Total Performance Task HPS) × 100

Performance Task Weighted Score = Performance Task Percentage × 0.50

Only applicable, created assessments are included.

**Summative Tests and Term Examination — 30%**

ST1 Percentage = (ST1 Score / ST1 HPS) × 100

ST2 Percentage = (ST2 Score / ST2 HPS) × 100

Term Exam Percentage = (Term Exam Score / Term Exam HPS) × 100

Summative Component Percentage = (ST1 Percentage × 0.30) + (ST2 Percentage × 0.30) + (Term Exam Percentage × 0.40)

Summative Weighted Score = Summative Component Percentage × 0.30

**Initial Grade**

Initial Grade = Written Work Weighted Score + Performance Task Weighted Score + Summative Weighted Score

The calculation uses fixed component weights without redistributing weights between categories.

When no Written Work or Performance Task assessments were created, the corresponding category contributes zero to the Initial Grade under the implemented transformation rule.

If an assessment was created but the learner has no recorded score or the score is blank, the score contributes zero raw points while the assessment's HPS remains included.

**Term Grade**

Term Grade = Initial Grade converted using the prescribed transmutation table.

The transformation implementation reads the configured transmutation ranges from `config/transmutation_table.json`.

If the official table is unavailable or an Initial Grade does not match a configured range, the Term Grade remains pending rather than using an assumed conversion.

**Final Grade**

Final Grade = ROUND((Term 1 Grade + Term 2 Grade + Term 3 Grade) / 3)

The Final Grade uses the three transmuted Term Grades, not the original Initial Grades.

The implementation uses half-up rounding to produce a whole-number Final Grade.

### 7.2 Record Reconciliation

Record reconciliation verifies that the student-subject-term combinations and assessment calculations processed during transformation are properly accounted for.

Because the Transformation Stage performs record matching, filtering, and aggregation, the number of output records is not expected to equal the number of source assessment or score records.

The Transformation Stage generates term-level results for three academic terms for each valid student-subject combination.

The following reconciliation principles are applied:

| Reconciliation Target | Validation Rule | Purpose |
|---|---|---|
| Student Records | Identify students with assigned subjects and record students excluded because they have no assigned subjects. | Support traceability of student processing. |
| Subject Records | Match assigned subject identifiers to cleaned subject records and document invalid subject assignments. | Maintain correct student-subject relationships. |
| Student-Subject-Term Combinations | Account for generated term results and combinations rejected before term processing. | Reconcile transformation processing counts. |
| Written Work Assessments | Calculate category scores and HPS using applicable assessments that were actually created. | Prevent incorrect score aggregation. |
| Performance Task Assessments | Calculate category scores and HPS using applicable assessments that were actually created. | Maintain correct category calculations. |
| Summative Assessments | Process ST1, ST2, and Term Examination using their required sequence and component weights. | Maintain accurate Summative calculations. |
| Excluded Records | Record excluded records and their corresponding reasons. | Support investigation and traceability. |
| Generated Outputs | Verify the existence and expected structure of the transformed JSON files. | Ensure output availability for validation and loading. |

The implemented transformation reconciliation formula is:

**Student-Subject-Term Combinations Considered = Term Results Generated + Combinations Rejected**

The number of considered combinations is based on the three academic terms for each assigned student-subject combination that enters processing.

Incomplete term results are still generated outputs and are not automatically counted as rejected combinations.

Students without assigned subjects are documented separately as excluded records and do not contribute to the counted student-subject-term combinations.

For assessment aggregation, the validation process checks the score and HPS values represented in the generated grading components rather than assuming that source assessment record counts must equal output record counts.

This approach supports reconciliation of transformed results while accounting for the pipeline's aggregation and filtering operations.

### 7.3 Severity and Validation Handling

Validation checks are classified according to their potential effect on the reliability of the transformed data.

**Critical Errors**

Critical errors indicate that the generated data may be incorrect or unsuitable for loading.

Examples include:

- Missing required identifiers.
- Duplicate student-subject-term results.
- Invalid student or subject references.
- Invalid term values or data types.
- Assessment percentages outside the allowed range.
- Incorrect grading weights or calculations.
- Incorrect available Term Grade transmutation values.
- Incorrect calculated Final Grades.
- Missing or unreadable required output files.

If one or more critical validation checks fail, the overall validation status is set to `FAILED`.

The validation flow raises an exception to prevent the validation stage from completing successfully. The Load Stage should not proceed until the critical issues are resolved.

**Non-Critical Warnings**

Non-critical warnings identify issues that require review but do not automatically stop the validation flow.

Examples include:

- Initial Grades awaiting official transmutation.
- Student-subject results without completed Final Grades.
- Excluded transformation records without properly documented reasons.

If non-critical checks fail and no critical failures are detected, the overall validation status becomes `WARNING`.

The warnings are recorded in the validation log for investigation.

**Overall Validation Status**

| Status | Meaning | Handling |
|---|---|---|
| `SUCCESS` | All performed validation checks passed. | The validation stage completes successfully. |
| `WARNING` | No critical failures occurred, but non-critical issues remain. | The validation stage completes and records warnings for review. |
| `FAILED` | One or more critical validation checks failed. | The validation stage raises an error, and loading should be blocked until issues are resolved. |

A `WARNING` status does not mean that all official grades have been calculated.

It indicates that the performed critical validation checks passed while some grading results or supporting information remain incomplete.

### 7.5 Expected Result

After transformation validation, the generated JSON files should contain consistent student and subject identifiers, valid academic terms, unique student-subject-term results, valid assessment percentages, and correctly calculated grading components and Initial Grades.

When the official transmutation table is available, completed Term Grades must match the prescribed conversion ranges.

Completed Final Grades must equal the average of the three transmuted Term Grades, rounded to the nearest whole number.

The validation process must identify and report discrepancies in data structure, references, grading calculations, and generated outputs.

The overall validation result is classified as `SUCCESS`, `WARNING`, or `FAILED`.

Critical validation failures prevent the validation stage from completing successfully and should block the Load Stage until the identified issues are corrected.

Non-critical warnings, including pending transmutation and incomplete Final Grades, are documented for review without automatically stopping validation.

The expected outcome is a traceable validation process that confirms the reliability of available transformed data, identifies incomplete grading results, and supports controlled handover to the Supabase PostgreSQL loading stage.
